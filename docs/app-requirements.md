# Вимоги до застосунку «Що в холодильнику»

## 1. Загальний опис

**«Що в холодильнику»** (англ. *What's in the Fridge*) — веб-застосунок для обліку
продуктів у домашньому холодильнику, морозилці та коморі, контролю термінів
придатності й підбору рецептів з того, що вже є вдома.

Проблема, яку розв'язує застосунок: користувачі купують продукти, що вже є вдома,
забувають про терміни придатності та викидають зіпсовану їжу. Застосунок дає одне
місце, де видно, що є вдома, що скоро зіпсується і що з цього можна приготувати.

Межі застосунку (що **не** входить в обсяг курсу): розпізнавання продуктів за фото
чи чеком, інтеграція з магазинами й доставкою, мобільні нативні застосунки,
розрахунок калорійності, спільний доступ кількох домогосподарств у реальному часі.

## 2. Цільові користувачі

| Роль | Опис | Основна потреба |
|---|---|---|
| Власник домогосподарства | Дорослий, який купує продукти й планує харчування для себе чи сім'ї | Бачити залишки, не купувати зайве, планувати меню |
| Студент / людина, що живе сама | Обмежений бюджет, готує нерегулярно | Використати продукти до завершення терміну, швидко знайти рецепт |
| Адміністратор (розробник) | Студент-розробник у ролі адміністратора | Наповнювати каталог рецептів, переглядати журнал подій |

## 3. Функціональні вимоги

Пріоритети подано за методом MoSCoW (M — must, S — should, C — could).

| ID | Вимога | Пріоритет | Критерій приймання |
|---|---|---|---|
| FR-01 | **Облік продуктів (CRUD).** Додавання, редагування, видалення продукту: назва, категорія, кількість, одиниця виміру, місце зберігання (холодильник / морозилка / комора), дата придбання, термін придатності. | M | Усі операції доступні через UI та REST API; невалідні дані відхиляються з кодом 400 і зрозумілим повідомленням. |
| FR-02 | **Пошук, фільтрація, сортування** продуктів за назвою, категорією, місцем зберігання та терміном придатності. | M | Фільтри комбінуються; результат на 1 000 записів повертається менш ніж за 300 мс. |
| FR-03 | **Контроль термінів придатності.** Автоматичний статус продукту: `fresh`, `expiring` (≤ 3 днів до кінця терміну), `expired`; окремий список «Скоро зіпсується» та підсвічування в UI. | M | Статус обчислюється детерміновано чистою функцією з покриттям тестами граничних дат (сьогодні, +3 дні, учора). |
| FR-04 | **Каталог рецептів.** Перегляд рецептів (назва, інгредієнти з кількістю, кроки, час приготування); адміністратор може додавати й редагувати рецепти; початковий seed-набір ≥ 30 рецептів. | M | Рецепти завантажуються з seed-файлу при ініціалізації БД. |
| FR-05 | **Підбір рецептів за наявними продуктами.** Для кожного рецепта обчислюється відсоток збігу інгредієнтів і список відсутніх; рецепти, що використовують продукти зі статусом `expiring`, мають вищий пріоритет. | M | Алгоритм ранжування покритий unit-тестами на фіксованому наборі даних з очікуваним порядком. |
| FR-06 | **«Приготувати» рецепт.** Підтвердження приготування автоматично зменшує кількість використаних продуктів у холодильнику. | S | Залишок не стає від'ємним; операція атомарна (транзакція БД). |
| FR-07 | **Список покупок.** Формування зі списку відсутніх інгредієнтів рецепта, ручне додавання позицій, позначка «куплено», після якої позиція переноситься до продуктів. | S | Перенесення створює продукт із датою придбання = сьогодні. |
| FR-08 | **Автентифікація.** Реєстрація та вхід за email і паролем; кожен користувач бачить лише власні дані. | S | Запит до чужого ресурсу повертає 404; доступ без сесії — 401. |
| FR-09 | **Журнал і статистика.** Журнал подій (додано / спожито / списано як зіпсоване) та статистика за період: кількість спожитих і викинутих продуктів. | C | Статистика за місяць відповідає записам журналу. |
| FR-10 | **Імпорт / експорт** списку продуктів у JSON. | C | Експорт → імпорт у порожній акаунт дає ідентичний набір продуктів. |

## 4. Нефункціональні вимоги

Сформульовано з урахуванням характеристик якості ISO/IEC 25010 в обсязі,
розумному для навчального проєкту.

| ID | Характеристика | Вимога |
|---|---|---|
| NFR-01 | Продуктивність | Час відповіді API p95 < 300 мс на локальній машині при 1 000 продуктів і 100 рецептах; первинне завантаження SPA < 2 с. |
| NFR-02 | Безпека | Паролі зберігаються лише як хеш (bcrypt); сесія — JWT у cookie з `HttpOnly`, `SameSite=Lax`; усі вхідні дані валідуються схемами zod; секрети лише в `.env`, який не потрапляє в git. |
| NFR-03 | Надійність | Зміни схеми БД — лише через міграції Prisma; операції, що змінюють кілька таблиць, виконуються в транзакції. |
| NFR-04 | Супровідність | TypeScript у режимі `strict`; ESLint + Prettier без помилок; покриття тестами доменної логіки (`packages/shared`) ≥ 80 %, API ≥ 60 %; повідомлення комітів за Conventional Commits. |
| NFR-05 | Тестованість | Доменна логіка (статуси термінів, підбір рецептів, списання) реалізована як чисті функції без залежності від БД і фреймворку. |
| NFR-06 | Зручність використання | Інтерфейс українською мовою; адаптивна верстка від 360 px; основні дії — не більше 3 кліків від головної сторінки. |
| NFR-07 | Переносимість | Запуск локально однією командою (`npm install && npm run dev`) на Windows / macOS / Linux з Node.js 24 LTS; БД SQLite не потребує окремого сервера. |
| NFR-08 | Вимірюваність | Кожна функціональна вимога має автоматизований тест або чек-лист приймання, що дозволяє об'єктивно оцінити «задача виконана правильно» (потрібно для ПР № 7). |

## 5. Технологічний стек

| Шар | Технології | Обґрунтування |
|---|---|---|
| Мова | TypeScript (strict) | Єдина мова для фронтенду, бекенду та спільних типів; статична типізація зменшує кількість помилок агента. |
| Фронтенд | React 19, Vite, React Router, TanStack Query | Поширений стек, який добре знає LLM; швидка збірка. |
| Бекенд | Node.js 24 LTS, Express, zod | Мінімалістичний REST API; zod-схеми спільні з фронтендом. |
| БД / ORM | SQLite + Prisma ORM | Не потребує сервера; міграції та типізований клієнт. |
| Тести | Vitest, Supertest, React Testing Library, Playwright (e2e, опційно) | Один тестовий раннер для всіх пакетів. |
| Якість коду | ESLint, Prettier, `tsc --noEmit` | Детерміновані перевірки, які зручно запускати агенту й hooks. |
| Структура | Монорепозиторій npm workspaces: `apps/web`, `apps/api`, `packages/shared` | Чіткі межі модулів для архітектурних guardrails. |
| Контроль версій | Git, GitHub, Conventional Commits, гілки `feature/*` → `main` | Історія комітів як джерело даних для harness. |

Цільова структура репозиторію застосунку:

```

├── ЗАВДАННЯ.md
├── README.md
├── docs/
│   ├── app-requirements.md      # цей документ
│   ├── harness-requirements.md  # вимоги до agent harness
│   └── adr/                     # архітектурні рішення (з ПР № 2)

│   └── api/                     # Express REST API + Prisma
├── packages/
│   └── shared/                  # zod-схеми, типи, доменна логіка
├── mcp-server/                  # MCP-конектор до vault (ПР № 3)
├── .claude/                     # harness: settings, hooks, skills, agents (ПР № 4–6)
```

## 6. Обрана агентна IDE

**Claude Code** (CLI та розширення для VS Code).

| Критерій курсу | Підтримка в Claude Code |
|---|---|
| Підключення зовнішніх MCP-серверів | Так: `claude mcp add` або файл `.mcp.json` у корені проєкту (спільна для репозиторію конфігурація). |
| Виконання bash-команд у робочій директорії | Так: вбудований інструмент Bash (git, npm, тести, лінтер). |
| Проєктні інструкції та конвенції | Так: файл `CLAUDE.md` у корені репозиторію читається на початку кожної сесії. |
| Перехоплення дій (hooks) | Так: події `PreToolUse`, `PostToolUse`, `SessionStart`, `UserPromptSubmit`, `Stop` та ін. у `.claude/settings.json`; `PreToolUse`-hook може заблокувати дію (exit code 2 або `permissionDecision: "deny"`) чи вимагати підтвердження (`"ask"`). |
| Правила дозволів | Так: `permissions.allow / ask / deny` у `.claude/settings.json` прямо відповідають трьом рівням guardrails allow / warn / block. |
| Skills | Так: `.claude/skills/<назва>/SKILL.md`. |
| Оркестрація ролей | Так: subagents у `.claude/agents/*.md` з власними інструкціями та набором інструментів. |

Обґрунтування: у Claude Code всі механізми, потрібні в ПР № 3–6 (MCP, hooks,
правила дозволів, skills, subagents), є нативними, працюють локально в одній
сесії CLI / VS Code і конфігуруються файлами в репозиторії (`CLAUDE.md`,
`.claude/`, `.mcp.json`). Конфігурація harness тому версіонується разом із кодом
і відтворюється на будь-якій машині. Cursor має порівнянний набір можливостей
(проєктні hooks у `.cursor/hooks.json` з рішеннями allow / deny / ask, правила,
MCP) і є прийнятною альтернативою; hooks GitHub Copilot задокументовані для
cloud agent і Copilot CLI. Вирішальні переваги Claude Code для курсу —
декларативні правила `permissions.allow / ask / deny`, що прямо відповідають
трьом рівням guardrails, окремі subagents з обмеженим набором інструментів для
ПР № 6 і наявність документації Claude Code у списку літератури курсу. Доступ до Claude Code — за підпискою Claude або через
акаунт Anthropic Console. Вибір фіксується до кінця курсу.
